# product view

the product unit is a useful personal outcome with less human coordination.
tool count, uptime and model activity are supporting measurements.

## who it serves

- a person connecting an existing agent to their own accounts and devices;
- an agent recovering context, choosing a route and completing a delegated task;
- a builder adopting one component or improving an interface;
- an operator keeping an installation recoverable across machines and updates.

each adopter has their own credentials, infrastructure and permissions. the
current direction is independent installations. a hosted multi-user service
would need separate account isolation, access control, support and cost design.

## product shape

1. choose one useful scenario and the smallest sufficient set of pieces;
2. obtain a working component from its owner and use your own account;
3. reach one independently verified result;
4. continue through restart and perform an upgrade with rollback;
5. compose a second component when it removes a real limitation.

the public hub makes these boundaries visible. a private source link is not an
installation funnel. an explanation request should receive a useful explanation.

## evidence to collect

measure time to first useful result, required human interventions, successful
continuations, duplicate effects, recovery effort and maintenance cost. retain
the denominator and scenario. do not invent adoption figures or treat a sent
notification as proof that it helped a person.

## present product gaps

independent packaging, compatibility ranges, recipient installation receipts and
portable configuration remain uneven across components. track those gaps in
the catalog and release work. a clean public map is the starting artifact.
