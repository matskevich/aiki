# functional view

think in outcomes before selecting tools.

| outcome | pieces that may help | useful completion |
| --- | --- | --- |
| find a prior decision in messages | messaging provider, source context | relevant source, time and coverage |
| arrange a meeting | messaging, calendar provider, operations context | agreed time and verified calendar state |
| complete a task across a disconnect | tasks, coordinator, device stage, watches | saved continuation and no repeated external effect |
| follow a task in a group or topic | conversation routing, task binding, messaging provider | correct participants and thread, one accountable task |
| ask the owner for a real decision | attention policy, notification channel, reply binding | exact question attached to the right task and resolved once |
| prepare a purchase | device/provider, payment policy, task state | compatible proposal within authority, then verified effect if authorized |
| produce content | domain context and media sources, common tasks | usable artifact and requested handoff |

these are composition patterns, not a promise that every integration is public
or supported in every client. a read-only search can stop with a useful source.
not every outcome requires durable orchestration.

## one task, several surfaces

a person can begin in a chat and inspect progress elsewhere. the coordinator
keeps the goal and receipts. a device agent owns a bounded stage. a topic or
linear card displays the same work rather than creating a competing obligation.
if a write outcome is unknown, recover its operation before trying another route.

## what stays personal

contacts, relationships, preferences, active commitments and domain records are
installation data. general skills describe how to retrieve and use them. they
should not embed another person's private context in a reusable release.
